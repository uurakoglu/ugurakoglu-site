Replacing Vesys with Capital Essentials while users kept working

We moved our electrical design users from Vesys to Capital Essentials. The aim was to keep every table in the database and every user as it was, so people could carry on working the next working day as if nothing had happened. This is the sequence we followed. The project started on 1 December 2023, and the production switch happened on the evening of 23 February 2024.

1. Test without users, with real-looking data

Before any change on the live system, the migration was rehearsed in an environment without users, using test projects, test data and test users. This is where the technical problems get found and fixed. The migration and upgrade in the test environment were completed on 29 January 2024.

2. Prepare the clients and the documents early

The client installation files and the instructions were prepared and shared with the team that does the installations before the migration date. That way the new clients were already in place on the day, and nobody was waiting for software.

3. A key user tests, and signs it off in writing

For the test environment, a key user from the Vesys user group was chosen, in agreement with that person's manager. The key user ran their own kind of work in the new version. We asked for written confirmation that nothing was wrong and that the migration could go ahead. This does two things: it catches problems from someone who knows the daily work, and it means the business has agreed to the change before it happens.

4. Upgrade after working hours

With that approval, the server upgrade from Vesys to Capital Essentials started after working hours on 23 February and was completed the same night. The leftover Vesys components were backed up and moved elsewhere, so a rollback remained possible if anything unexpected appeared.

5. The next working day

When users arrived on the next working day they started Capital Essentials instead of Vesys, and continued on their projects with their existing libraries and data. There was no interruption.

Documentation is part of the work

I document everything I do, and this project was a good example. Before the migration I wrote a server-side document covering the installation, the upgrade and the other tasks involved, and a step-by-step checklist for the live cutover. On the night I followed my own checklist: stop a service, check it, run the next migration step, check again, move on. No step depended on memory.

That also confirmed the value of the rehearsals. The test migration proved the steps in the document, and the checklist then made the real thing calm and repeatable. It matters beyond this project: the next time a similar migration comes up, even if I am not there, people can follow the documents, see the problems we met before and their solutions, and avoid solving them again.

Two versions side by side

Another team still uses an older Vesys version, so I administer both that and Capital Essentials. One group moving does not mean everyone moves at once, so the two environments run side by side.
